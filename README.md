# Nemo Design System

Token-driven web components built with [Stencil](https://stenciljs.com), distributed to web / React / Vue / Angular as typed, versioned npm packages. Color tokens are generated from a single DTCG source via Style Dictionary — **no hand-written color CSS**.

This is an **npm-workspaces monorepo**:

```
packages/
  tokens/       @nemo/tokens     — generated CSS custom properties + typed TS (Style Dictionary)
  components/   @nemo/components — the Stencil web-component library (source of truth)
  react/        @nemo/react      — typed React wrappers (generated via @stencil/react-output-target)
  vue/          @nemo/vue        — typed Vue 3 wrappers (generated via @stencil/vue-output-target)
  angular/      @nemo/angular    — typed Angular wrappers (generated via @stencil/angular-output-target,
                                    built with ng-packagr)
```

`@nemo/components`, `@nemo/tokens`, `@nemo/react`, `@nemo/vue`, and `@nemo/angular` are versioned and released **in lockstep** via Changesets (see `.changeset/README.md`).

## Requirements

- Node.js 18+
- npm 9+ (for workspaces)

## Install & build

```bash
npm install        # installs + symlinks all 5 workspace packages
npm run build       # tokens -> components (+ wrappers) -> react -> vue -> angular, in order
```

Other root scripts:

```bash
npm run build:core   # just @nemo/tokens + @nemo/components (fastest inner loop)
npm start             # tokens build + Stencil dev server (serves packages/components/src/index.html)
npm test              # Stencil spec + e2e tests (packages/components)
npm run storybook     # Storybook on :6006 — build first so loader/ + custom-elements.json exist
npm run changeset     # describe a change for release (see .changeset/README.md)
```

Package-scoped: `npm run build -w @nemo/tokens`, `npm run build -w @nemo/components`, etc.

## Distribution & release (Phase 4)

### Framework wrappers

`@nemo/components`'s `stencil.config.ts` configures three output targets that generate the framework wrapper _source_ into the sibling packages on every `npm run build -w @nemo/components`:

| Output target         | Generates into                                     | Consumed by     |
| --------------------- | -------------------------------------------------- | --------------- |
| `reactOutputTarget`   | `packages/react/src/components/stencil-generated/` | `@nemo/react`   |
| `vueOutputTarget`     | `packages/vue/lib/components.ts`                   | `@nemo/vue`     |
| `angularOutputTarget` | `packages/angular/src/lib/stencil-generated/`      | `@nemo/angular` |

Each wrapper package then has its own `build` script that compiles that generated source + its hand-written entry point (`index.ts`/`plugin.ts`/`public-api.ts`) into `dist/`. **Build order matters** — tokens, then components (which generates the wrapper sources), then the three wrappers — which is exactly what the root `npm run build` does.

`@nemo/angular` is built with **ng-packagr** (the same tool the Angular CLI's library builder wraps), producing a proper Angular Package Format output in `packages/angular/dist` — that `dist` folder (not the package root) is what gets published; ng-packagr writes its own `package.json` there.

### Package metadata

Every publishable package (`@nemo/tokens`, `@nemo/components`, `@nemo/react`, `@nemo/vue`) has a correct `exports` map, `main`/`module`/`types`, `sideEffects`, and `files` allowlist — verified with `npm pack --dry-run` in each package directory. `@nemo/angular`'s equivalent fields are generated by ng-packagr into `dist/package.json`.

### Versioning — Changesets

```bash
npx changeset            # describe a change (interactive)
npx changeset version     # apply version bumps + changelogs
npm run build && npx changeset publish
```

A **token rename or prop removal is a breaking (major) change**.

### Smoke-testing a consumer app

See `packages/react/README.md` and `packages/vue/README.md` for the exact steps to link a throwaway app against these packages locally (`npm install <path-to-package>` or `npm link`) before publishing.

## Storybook & testing (Phase 3)

Stories live next to each component (`packages/components/src/components/<name>/*.stories.tsx`) plus a `Foundations/Colors` story. Storybook uses the official `@stencil/storybook-plugin`; the Custom Elements Manifest drives auto-generated prop/event/slot/CSS-var tables, and a toolbar **theme toggle** flips `[data-theme="dark"]`.

```bash
npm run build         # generate loader/ + custom-elements.json + tokens
npm run storybook     # then open http://localhost:6006
```

Three testing layers:

1. **Behavior** — Stencil spec + e2e: `npm test`.
2. **Accessibility** — `@storybook/addon-a11y` (axe) scans every story; the a11y panel lists
   violations. Phase 5 makes these build-blocking in CI.
3. **Visual regression** — Chromatic snapshots every story. Create a project at chromatic.com,
   then run with its token:

   ```bash
   cd packages/components
   npx chromatic --project-token=<your-token>
   # or set CHROMATIC_PROJECT_TOKEN and run `npm run chromatic -w @nemo/components`
   ```

## Token architecture

```
packages/tokens/tokens/
  primitive/            raw tonal scales resolved from Figma (the source material)
  semantic/
    light/              role layer for the light theme — aliases primitives
    dark/               role layer for the dark theme  (see NOTES below)
```

Two tiers:

- **Primitive** — raw palette tones (e.g. `palette.primary.40`). Build-time source only.
- **Semantic** — the role layer components consume (e.g. `color.primary`, `color.on-surface`).

`@nemo/tokens`'s build emits:

- `dist/tokens.css` — `--nemo-color-<role>` custom properties. Light under `:root`,
  dark under `[data-theme="dark"]`. `@nemo/components` consumes this directly as its
  Stencil `globalStyle` (`../tokens/dist/tokens.css`), and Storybook imports
  `@nemo/tokens/tokens.css`.
- `dist/tokens.js` + `dist/tokens.d.ts` — a typed, theme-aware map of role → `var(--nemo-color-<role>)`.
  Import `@nemo/tokens` in components/consumers for autocomplete instead of stringly-typed `var(--…)`.

**Components reference the semantic tier only** — never a primitive, never a raw hex. This is
what makes theming and rebranding possible (enforced by a lint rule in Phase 5).

```ts
import { nemoColor } from '@nemo/tokens';
// nemoColor.primary === 'var(--nemo-color-primary)'
```

## Components

- **`nemo-button`** — `variant` (primary/secondary/tertiary), `size` (medium/small), `icon-only`,
  `loading`, `disabled`, `full-width`; `leading-icon`/`trailing-icon` slots; `nemoClick` event.
- **`nemo-text-input`** — `label`, `value`, `placeholder`, `helper-text`, `validation-state`
  (none/error/warning) + `validation-message`, `disabled`, `readonly`, `required`, `tooltip`,
  `expandable`, `name`/`input-id`; `nemoInput`/`nemoChange` events. Accessible read-only and ARIA
  (`aria-invalid`/`aria-describedby`/`aria-required`).

Both reference the semantic color tokens only. See each component's generated `readme.md`
(after a build) for the full prop/event/slot tables.

> **Consumers must load the global token stylesheet once** (it carries the `:root`
> `--nemo-color-*` custom properties). Stencil's lazy loader does **not** auto-inject it.
> Add a `<link rel="stylesheet" href=".../nemo-ds.css" />` (the compiled `globalStyle`,
> emitted to `dist/nemo-ds/nemo-ds.css`) or `import '@nemo/components/dist/nemo-ds/nemo-ds.css'`.
> Without it, components fall back to black/white.

## Quality gates & CI/CD (Phase 5)

### Linting & formatting

```bash
npm run lint            # eslint . && stylelint ... && prettier --check .
npm run lint:eslint      # ESLint (typescript-eslint + @stencil/eslint-plugin) — flat config, eslint.config.mjs
npm run lint:css         # Stylelint (stylelint-config-standard) — .stylelintrc.json
npm run lint:format      # Prettier --check
npm run format           # Prettier --write
npm run typecheck        # tsc --noEmit across all 5 packages
```

ESLint's flat config applies `@stencil/eslint-plugin`'s recommended rules (plus a `stencil/required-prefix: nemo` rule) only to `packages/components/src/components/**/*.tsx` — the rest of the monorepo gets `typescript-eslint`'s recommended rules. Generated output (`dist/`, `loader/`, `custom-elements.json`, the framework-wrapper `stencil-generated/` dirs, `packages/vue/lib/components.ts`) is excluded from ESLint, Stylelint, and Prettier alike — it's built, not hand-edited (CLAUDE.md).

### Token-discipline guard

`.stylelintrc.json` adds a `declaration-property-value-disallowed-list` rule scoped to `packages/components/src/components/**/*.css` that fails on a raw `#hex`, `rgb()`/`rgba()`, `hsl()`/`hsla()`, or a primitive `var(--nemo-palette-*)` reference — only `var(--nemo-color-*)` semantic tokens are allowed, enforcing the CLAUDE.md token-discipline rule. (This caught one real violation during setup — `button.css`'s hover shadow used a raw `rgba(...)`; it now reads `color-mix(in srgb, var(--nemo-color-shadow) 32%, transparent)`.)

`npm run tokens:validate` (wired into CI's `validate` job) checks the DTCG source itself: every token resolves a `$type`, every semantic `{alias}` reference resolves to a real primitive path (no orphans), and no token path is defined twice across sibling files (no duplicates).

### Commit hygiene

`husky`, `lint-staged`, `commitlint`, and their configs (`commitlint.config.mjs`, the `lint-staged` field in the root `package.json`, and the `prepare` script) are in place, but the `.husky/` hook files themselves need to be generated locally (git hook scripts aren't something this assistant can write directly). One-time setup:

```bash
npm install                     # runs "prepare": "husky" via npm's prepare lifecycle
npx husky init                  # creates .husky/pre-commit
echo "npx lint-staged" > .husky/pre-commit
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg
```

After that, every commit runs `lint-staged` (ESLint/Stylelint/Prettier on staged files) and every commit message is checked against `@commitlint/config-conventional` (Conventional Commits — required for Changesets to infer semver).

### CI/CD — GitHub Actions

- **`.github/workflows/ci.yml`** (PRs + pushes to `main`): `validate` (token schema, lint, typecheck) → `build` (tokens → components → wrappers, uploaded as an artifact) → `test` (Stencil spec/e2e + Storybook `test-storybook` a11y gate — stories with `parameters.a11y.test = 'error'` fail the job on a WCAG violation) → `visual` (Chromatic, needs a `CHROMATIC_PROJECT_TOKEN` repo secret) → on `main` only, `storybook-deploy` (static Storybook to GitHub Pages, needs Pages enabled for the repo).
- **`.github/workflows/release.yml`** (push to `main`): runs `changesets/action` — opens/updates a "Version Packages" PR while changesets are pending, and once merged, publishes all five packages to npm with provenance (needs an `NPM_TOKEN` repo secret with publish rights).

Both workflow files are new and haven't run in GitHub Actions yet — the first PR against this repo is the real test.

## Docs, icons & governance (Phase 6)

### Usage documentation

Each component has an MDX docs page alongside its stories (`button.mdx`, `text-input.mdx`,
`icon.mdx`), plus `foundations/tokens.mdx` for the token architecture. Content — purpose,
variant/state guidance, Do/Don't, content rules, and the accessibility checklist — is pulled from
the Figma file's own documentation frames (Button node `4-31`, Text Input node `4-33`), not
reinvented. The prop/event/slot API tables stay generated from `custom-elements.json` (via each
MDX page's `<Controls of={...} />`) — nothing here duplicates that by hand.

### Icons

`nemo-icon` is a small, tokenized icon component:

```
npm run icons:build -w @nemo/components   # SVGO-optimizes icons/*.svg -> icons.generated.ts
```

```html
<nemo-button variant="secondary">
  <nemo-icon slot="leading-icon" name="search"></nemo-icon>
  Search
</nemo-button>
```

Every icon strokes in `currentColor` (no hex, ever) and is decorative (`aria-hidden`) unless given
a `label`. The Nemo Figma file has no icon component library to trace values from, so the current
10-icon set (`arrow-right`, `search`, `mail`, `eye`, `eye-off`, `close`, `check`, `chevron-down`,
`alert-circle`, `alert-triangle`) is hand-authored, not Figma-sourced — see `docs/ICONS.md` for the
pipeline and how to add more.

### Governance

`CONTRIBUTING.md` covers proposing a token/component, the Definition-of-done bar, and the
commits/changesets flow. `docs/DEPRECATION.md` covers deprecating (never silently removing) a
token or prop. `.github/CODEOWNERS` covers the token source and component directories (placeholder
handles — replace with real owners before this is load-bearing). `.github/ISSUE_TEMPLATE/
rfc-token-or-component.md` is the proposal template CONTRIBUTING.md points to.
